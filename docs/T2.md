# Apple T2 Research Track

## Status

The T2 track is exploratory only, isolated under experimental/t2-offload, and disabled by default. There is no assumption that ordinary macOS software can run arbitrary workloads on the T2.

## Research question

Can any narrowly scoped, technically supported T2 operation reduce total system energy after accounting for communication, wakeup, transfer, and integration costs without weakening device security or reliability?

## Current boundary

Apple's platform-security documentation describes the T2 as part of the secure boot chain and as a platform for the Secure Enclave on supported Intel Macs. The reviewed public documentation does not describe a general-purpose app execution interface. MacLean therefore treats arbitrary workload offload as an unproven feasibility question, not an available feature. The T2 is not treated as a substitute for Intel CPU/GPU execution. Secure Enclave functions, boot/security functions, and firmware boundaries must not be bypassed or repurposed.

## Permitted initial work

- Read authoritative Apple platform-security and developer documentation.
- Inventory public macOS interfaces that report T2 presence and supported functions.
- Review published open-source research at source level and record its model/OS scope.
- Separate documented interfaces from reverse-engineered or private interfaces.
- Estimate data movement, wakeup, protocol, and integration energy before proposing an experiment.

## Out of scope

- Firmware modification or exploitation.
- Boot ROM, Secure Boot, FileVault, Secure Enclave, or activation-security changes.
- Arbitrary code loading or workload delegation over undocumented protocols.
- Kernel extensions or privileged helpers that weaken platform protections.
- Treating an observed device endpoint as authorization to execute code on it.

## Feasibility gate

Before implementation, a written proposal must identify:

1. A documented, supported interface and eligible workload.
2. Device and OS versions known to support it.
3. A threat and failure analysis with no security downgrade.
4. A safe cancellation and recovery path.
5. A controlled measurement showing likely net energy benefit after communication overhead.

If no supported interface exists, the conclusion should be that T2 offload is unavailable for MacLean, rather than escalating to invasive access.

## Open questions

- What T2-related functions are publicly exposed to ordinary macOS apps?
- Are any functions programmable for user workloads, or are they fixed-function only?
- What happens across sleep, wake, OS updates, and T2 firmware updates?
- Can the expected computation save more energy than data movement and protocol overhead?
- Which primary sources establish support on the exact target?
